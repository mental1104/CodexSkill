# 完整场景与真实边界案例

以下以两端文件传输说明测试证明了什么，不规定框架、协议、端口或固定 fixture 数量。先服从已评审的 Contract 与当前 Phase。

## 案例一：完整测试可以 RED，但不能只写半条链路

已确认的业务是：上层提交任务，对端传输文件，接收端校验和发布，上层取得最终结果。

| 写法 | 实际证明的范围 | 问题或取舍 |
|---|---|---|
| 执行传输到 staging，最后无条件失败；注释说发布和 Result 以后再补 | 数据面能到 staging | 人为失败不会随生产能力补齐而消失，最终需求还不是可执行断言 |
| 通过约定的上层入口提交任务，等待结果，并写出正式文件、内容、摘要和返回字段断言 | 完整公开契约已经表达；当前可能在入口未实现处自然失败 | 后续断言可以暂时到不了，但不能缺失或由 fixture 代做 |

```text
第一版：调用传输组件 → 检查 staging → 无条件 FAIL

改进后：上层提交公开请求
       → 收集协议要求的进度
       → 等待最终 Result
       → 检查成功、任务身份、字节数和发布位置
       → 独立检查正式文件内容与摘要，以及 staging 的最终状态
```

Phase 2 不实现生产发布逻辑，也不在 fixture 里重命名文件来满足最后的断言。缺少接口声明时可以按阶段允许范围补最小接缝，并明确编译缺口；接缝暂时返回“未实现”可以如实记录，但仍须保留完整业务断言。依赖没装好不能记成“业务按预期 RED”。

反向情形：如果本轮只评审了 rsync 组件的数据搬运，检查 staging 就可以是完整的组件测试；不要顺手添加未确认的上层协议、服务发现或原子发布要求。某些断言可能因前置失败而无法执行，也不要求人为绕过前置失败跑到结尾。

## 案例二：真实网络不等于真实业务边界

需求明确包含“调用方只提供设备身份，由服务自己发现地址、连接对端并传输”。错误做法是一个对象掌握两端目录，测试从它的本地监听表取出远端端口再塞给调用方；即使中间真的发了 UDP 或 TCP 报文，也可能绕过了约定的发现和跨服务交互。

改进后的职责可以是：

| 参与方 | 承担的职责 |
|---|---|
| 进程 fixture | 按约定启动两端、准备各自的源数据与配置、等待就绪并回收资源 |
| 两端被测服务 | 各自管理本地资源，发布本端服务信息，通过约定发现机制获得对端地址，再经真实协议交互 |
| 上层应用 fixture | 通过公开客户端提交设备身份和文件参数，接收进度与最终结果 |
| 验收代码 | 从外部读取产物或证据，不在请求执行期间代做远端业务 |

服务读取自己的实际监听端口后发布是正常启动行为。需要避免的是调用方提前掌握远端地址并绕过被测发现路径；只测试“解析第三方公告”的场景也允许独立协议 peer 发布记录。发现缓存的命中可以合法满足契约，不要求每次请求都重新发包；缓存失效和重试按已约定语义验证。

用户要求双进程隔离时，用 fixture 管理真实子进程；区分实例的 Action 名称、目录和服务身份优先从既有配置或重映射入口注入，不向生产业务添加测试角色分支。单进程内两对象、两个独立进程和两台设备是不同的验证范围，报告时分别说明。

反向情形：单元测试可以用 mock 验证决策；明确允许协议替身的集成测试也不必启动所有真实服务。两轮顺序互传只能证明双向能力，不能据此声称验证了同时全双工。

## 案例三：限速是观察条件，不自动成为产品需求

用户只想让传输持续足够久，以便看到中间进度。可用 fixture 对真实传输施加限速，准备合适数据量，在上层公开反馈中观察中间字节推进，再检查终态和实际文件。

不能用 sleep 或预设反馈伪造进度，也不据此新增生产限速 API、共享带宽预算、公平性或吞吐达标要求。数值和等待窗口依实际环境确定，测试结束恢复本轮改变的状态。

如果需求确实包含生产 QoS 或共享预算，它们就是需要单独评审的产品契约，不能套用本例删除。双向共用 helper、循环或参数化的选择也由当前场景与测试框架决定，不固定成“一定一个测试”或“一定两个测试”。

## 案例四：覆盖率要能归因到实际业务场景

用户希望通过多种集成场景覆盖传输主流程和失败分支。测试进程虽然生成了覆盖率文件，但业务库未纳入采集；或者复用了之前单测留下的数据，这时一个很高的比例也不能回答集成场景覆盖了什么。

改进后应能说明：

1. 本次测量对应哪个版本、配置和业务代码范围，哪些目标已纳入采集。
2. 清晰区分本次集成 suite 与其他测试的数据；列出实际执行的场景以及失败项。
3. 分别报告工具支持的行、函数、分支覆盖率，以及第三方、生成代码、fixture 等排除范围和原因；不能为了提高比例移走未覆盖的业务代码。
4. 从未覆盖业务分支回到已有需求，判断应补哪个公开场景，而不是直接为内部函数补一个凑数字的单测。

例如“准备接收被拒绝”“对象下载中断”“摘要不一致”“取消后临时文件清理”可以分别覆盖实际错误传播。场景应通过约定的外部条件触发，被测代码自己走到这些分支；不能让 fixture 执行上传、下载、校验和发布，再把它的覆盖率当作业务实现证明。

外部对象存储或云端控制服务允许被替换时，可用可插拔 fixture 提供确定性环境，核心编排和发布仍执行真实代码。这里验证的是该边界下的集成行为，不等于真实 SDK 或云网络已联调。

反向情形：没有覆盖率交付要求时，不自动引入采集工具或阈值。已有单测可以保留，难以通过集成稳定定位的局部不变量仍可有单测；要求集成场景贡献覆盖率不等于禁止所有单测。场景失败时采到的数据也可能有价值，但报告须保留失败事实，不能据百分比宣称业务通过。

## 案例五：自动回归与业务调用方手动使用

用户同时要求自动化闭环和手动使用方案。只给一条测试可执行文件命令，虽然能重复跑 fixture，仍无法告诉调用方真实使用模块时应该传什么参数、准备哪个文件、如何验收。

```text
自动化：fixture 准备依赖 → 公开客户端驱动真实业务 → 断言 → 框架清理

手动：说明依赖和两端配置 → 启动服务 → 准备真实输入文件
     → 用公开客户端提交实际请求 → 观察反馈与最终结果
     → 核对接收端正式文件和摘要 → 清理本轮状态
```

两套方案应对应同一份业务契约，并区分使用了哪些外部替身。手动方案可以沿用现有工具和环境，不能只写“看源码里的 fixture”，也不需要另造一个产品客户端。

反向情形：用户仅要求修复一个测试或给运行命令时，直接完成该请求，不擅自启动真实云服务或增加全套部署手册。
