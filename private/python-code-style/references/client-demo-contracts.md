# Python 对接示例与生成接口

适用于用户把示例作为上层服务对接指南，尤其是使用生成消息与异步反馈的客户端。以下为数据流和类型关系示意，不是完整可运行实现。

## 案例一：已有协议类型是契约来源

客户端已经可以导入接口生成器提供的 Goal、Feedback、Result。若再建一套字段完全相同的 dataclass、字典字段表或 Pydantic 模型，就会形成第二份协议；把所有内容改为 `Any` 也会丢失现有补全能力。

```text
真实接口定义 → 生成的请求/反馈/结果类型 → 实际客户端调用
                                         → 必要时转换为应用自己的领域结果
```

在主流程构造实际请求，关键字段有明确类型与含义。为真实第三方类型缺口做局部适配时限制动态边界；若应用结果需要合并本地文件证据等不同语义，可以建立相应 typed model，但不逐字段复制协议充当新事实源。外部通知 JSON 仍须按边界规则解析并校验后进入内部。

示例文档说明导入包如何由接口生成、构建和加载，不能把某个容器构建目录可引用描述为已经提供可分发的安装包。

反向情形：协议只有 JSON、没有现成可信类型时，按现有声明式边界建模规则处理；不因本例跳过校验，也不强行引入代码生成工具。

## 案例二：装饰器承接共同行为，保留类型与失败

用户明确要求示例主流程只展示对接，日志和异常统一封装。可以把入口日志、异常报告和退出码转换放入小型装饰器，把真正的资源获取/释放交给上下文管理；进度回调和请求结果处理仍作为对接内容可见。

```text
入口装饰器：统一日志 → 执行有类型的 main → 异常报告与明确失败退出
main：构造请求 → 创建公开客户端 → 传入 on_progress → 处理最终结果
资源上下文：初始化 → 提供客户端所需资源 → 正常/异常退出时释放
```

按目标 Python 版本保留参数与返回值的泛型关系，例如适用时用 `ParamSpec` 与返回类型变量，另用 `functools.wraps` 保留元数据；只有 wraps 不等于静态签名已保留。原函数的同步/异步性质也应保持。回调签名具体到反馈类型，不让包装层变成 `Callable[..., Any]`。

入口可以按 CLI 契约把异常转成非零退出码，并执行约定的失败通知与清理；不能吞错后返回成功、静默重试或把不确定的提交当作可安全重放。普通库函数仍按其异常契约传播，不套用 CLI 退出处理。无需装饰器时继续直接调用，不建立通用日志/异常框架。

## 案例三：IDE 看得见不等于运行依赖已齐备

运行容器能导入生成包，而宿主机 IDE 报 unresolved import 时，先确认工作区解释器、生成包位置及其接口版本。优先让编辑器连接实际开发环境或引用对应构建/安装路径。

确需把容器产物同步给宿主机索引时，使用真实生成文件、可重复的同步方式和忽略目录；说明接口变更后如何重新生成与同步，不手写假消息类消除红线。Python 生成代码可能依赖本机原生扩展、typesupport 或运行库，索引副本不能证明宿主机可以执行客户端。

核对模块解析/字段可见与实际运行分别提供证据；未操作编辑器时，不声称其界面诊断已消失。真实运行也无法 import 时，应处理实际包和依赖，不仅添加分析搜索路径。

## 场景回放

- 正向输入：写一个使用已有生成接口的 Python 上层客户端示例；明确端点、请求字段与进度，按用户要求把日志/异常装饰器化。观察是否保留真实客户端契约、具体回调及装饰后的类型，失败是否仍可见。
- 邻近反例：给普通库修一个函数，既无示例重排也无装饰器要求。不自动引入 CLI、catch-all、退出码或新框架。已有 SDK 类型与只有原始 JSON 的协议应分别选择复用与边界建模。
- 生成包只存在容器的输入：区分 IDE 索引修复和可运行依赖，不把同步文件当运行验证。本节定义回放，未记录独立会话或真实编辑器实测。
