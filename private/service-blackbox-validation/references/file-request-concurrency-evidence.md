# 文件请求与并发诊断案例

适用于按截图下载文件、复现文件不存在错误，以及核对测试流量是否影响另一客户端。以下为脱敏的证据判断示例，不是已运行的服务验收。

## 案例一：界面路径不一定相对于协议根目录

界面展示 `job-7/archive.tar`，请求需要命名空间 `capture`。原样提交后返回文件不存在，只能证明这组请求参数失败。

已有目录或列表证据若确认命名空间根目录下的实际文件是 `jobs/job-7/archive.tar`，再用包含 `jobs/` 的路径请求。分别保存原始参数与修正参数，以及各自的响应；这样既能复现界面错误，也能判断缺失目录层级是否解释差异。只把请求改到成功，不能证明界面已经修复。

```text
界面显示路径 → 原样请求及错误响应
协议根目录 + 当前目录/列表证据 → 修正后的相对路径 → 请求及完整产物核验
```

先使用已有源码、公开列表接口、配置或用户提供的目录证据。确实需要目标机检查时，沿用当前授权边界。证据缺失时说明尚未确认映射，不盲试命名空间、目录前缀或扩大机器检查范围。

条件改变时：协议返回的路径已经是规范相对路径或不透明标识，就按协议原值使用；用户只要求精确重放失败请求时，先完成重放，不悄悄替换成修正请求。

## 案例二：并发推断需要额度归属与时间线

若怀疑验收客户端占满了另一类业务的额度，先确认这些请求实际经过哪个调度入口，再读取该运行实例使用的配置。后台任务执行、授权或哈希准备、文件发送可能是不同资源；数值与名称不能证明共享关系。

建立当前窗口内的最小事件表，包含请求标识、来源或来源未知、所属预算、到达时间、开始时间和实际释放时间。本轮自有下载也列入；提供可重复执行的命令时，说明是否还有旧请求在运行，避免新增流量后误读原现象。

| 观察 | 能支持的结论与限制 |
|---|---|
| 第二条请求在第一条释放后才到达 | 当前服务未观察到这两条请求同时排队；上游调度是候选原因，需客户端时间线定位 |
| 两条请求已到达，第二条在第一条释放后才开始 | 可能存在服务端等待；仍需核对准入、准备及发送阶段，不能直接归因于某个配置项 |
| 多条发送开始事件重叠，未见完整释放记录 | 只能作重叠线索；须确认日志覆盖与释放语义，才能证明同时持有额度 |
| 没有限额拒绝日志 | 不能单独证明从未满载，系统也可能等待或缺少对应日志 |
| 请求同时被重置，附近出现发送异常 | 保留关联作为异常线索；未有进一步证据时，不归因为容量耗尽 |

无法识别客户端来源时，用“来源未确认的一组请求”，不能把它直接命名为 WebUI。日志缺少必要字段时，先说明缺口；补埋点、抓客户端 Network 或重放负载分别服从当前任务范围。

条件改变时：只要下载命令就交付命令，不额外运行并发试验；只读诊断则保留推断和后续验证点，不修改额度或服务部署。
