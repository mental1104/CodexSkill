# 服务黑盒验收

## 职责与边界

从公开协议、实际产物和服务日志证明一次业务操作完成，并使人可以重复执行、独立复查。适用于自动化黑盒测试和人工逐步验收，不依赖服务实现语言。

- 只处理当前约定的业务闭环和测试环境；已有执行、部署、源码和测试修改授权继续有效，不额外增加确认关卡。
- 用户只要命令或说明时，交付可执行步骤，不因此重跑整套测试或改服务。用户要求设计、实现或执行验收时，完成相应工作。
- 用户要求先只改源码、保留旧测试或暂不运行测试时，遵守本轮边界，标明未验证行为；不能把该选择变成长期免测规则。
- 普通补测试或手工验收不启动 TDD；用户明确要求测试先行或阶段评审时，组合 `tdd-workflow` 并服从当前阶段。
- 写测试、脚本或补业务日志前，加载 `code-comment-writing` 和适用的语言规范；C++ / Python 同时应用 `default-coding`。归档到 Obsidian 时另走 `ROUTER`，普通仓库手册不触发归档审批。

## 先固定验收对象

阅读当前协议、公开入口、已有测试启动方式和实际运行配置，明确源码版本、镜像或构建产物、目标服务和测试数据。以当前证据确认接口是否已经进入生产调用路径，区分健康、请求受理、任务终态和产物交付。

用简短映射组织需求、触发动作和独立验收依据。仅覆盖协议实际要求的场景；用户要验证全部用例时，先列全范围，再说明自动化覆盖与人工步骤的对应关系。尚未实现的能力应列为缺口；当前占位拒绝可以作为阶段回归，不能据此宣称目标生命周期已完成。

黑盒客户端只通过公开 HTTP / WebSocket 契约驱动业务，不链接或调用服务内部实现。独立文件核验、外部配置准备和日志采集属于夹具与证据层，不冒充公开接口行为。云平台替身、真实服务组件和设备实测的范围分别说明。

## 按可观察行为组织场景

优先跑通当前请求的最小完整成功路径，再按需求补充失败和并发分支：

| 验收对象 | 决定性证据 |
|---|---|
| 异步任务 | 受理响应取得有效 ID，查询或订阅达到真实终态；受理成功和进度 100% 不替代终态 |
| 文件传输与下载 | 测试源真实存在，独立读取源与目标的字节数、SHA-256；有客户端下载要求时，再核对实际下载正文 |
| 订阅与重连 | 确认订阅、快照、真实进度和终态；按协议接受已完成任务的终态快照，不等待协议不承诺补发的事件 |
| 取消、容量与清理 | 确认操作确实发生在运行或占用期间，再核对终态、产物与资源释放；断开观察不等于取消任务 |
| 能力或授权配置 | 在实际读取配置的容器或服务中准备真实文件；按契约验证缺失、禁用、损坏及恢复，不只 mock 读取结果 |
| 文件占用、删除与重启 | 制造实际持有连接或资源的条件，核对删除等待、释放后的访问行为与重启后的协议结果 |

大文件、取消和进度场景要检查实际生效的限速、数据量和超时，留出足够观察时间；不固定为某个文件大小或带宽。独立配置、限速及故障场景优先沿用仓库已有隔离夹具，并恢复本轮改变的测试状态。

## 用日志补齐证据

沿用仓库已有日志库、字段和等级：INFO 承载受理、开始、结束及关键生命周期，DEBUG 承载协议细节和节流后的进度。日志量大时，先提供本轮筛选与关键事件视图，再判断是否需要调整埋点或频率。

记录本轮时间范围、完整任务 ID，以及需要时的请求或连接 ID。按这些标识与字段边界精确过滤，再区分开始、过程和成功；不要把其他任务的日志或“已受理”当作执行成功。先核对实际日志格式与状态值，再写断言或 grep。缺少必要事件时，在已授权的源码范围内补充；只读任务则说明证据缺口。

成功必须同时满足协议结果与业务产物；进度证据应有真实字节或状态推进。取消、失败和预期拒绝使用各自验收条件，不因有 ERROR 日志就自动判失败，也不把它们标成成功下载。

每轮保存原始请求、状态码与响应体、WebSocket 帧、独立产物核验和相关容器日志。临时服务回收前归档其日志；查看归档时保留原始证据，避免用已消失容器的空输出覆盖。并发观察与操作使用各自的输出文件。

## 交付方式

用户要手工自测、playbook 或可粘贴的原子命令时，读取 [人工验收与原子命令](references/manual-acceptance.md)。先交付能立即执行的最小闭环；已有明确上下文时，不为回答一条命令重新扫描整套系统。

自动化测试沿用仓库入口并给出可从明确工作目录运行的命令。最终验收应对应同一版代码、镜像、夹具和工具；修正后重跑受影响场景，版本或共享基础发生变化才扩大回归，按用户要求完成全量验收。

报告区分静态检查、场景推演、实际调用和仍未验证的行为。运行结果附证据位置；仅凭 health、构建成功或测试数量不能宣布业务闭环通过。
