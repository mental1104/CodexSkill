# 中文代码注释规范

## 定位

这是所有代码编写与修改任务的强制伴随 Skill。

只要最终交付物包含以下任意内容，就必须在编码前先读取并应用本 Skill：

- 新增代码；
- 修改已有代码；
- 修复缺陷；
- 重构代码；
- 编写脚本；
- 编写测试、示例程序或最小可运行代码；
- 输出用户准备直接复制运行的代码片段；
- 编写存储过程、函数、触发器或复杂 SQL；
- 生成配置解析、迁移、构建、部署或运维代码。

本 Skill 是代码质量约束，不替代语言、框架、仓库或任务专用 Skill。应当与其他 Skill 组合使用。

## 核心目标

注释应让首次阅读代码的人无需反复追踪调用方，就能回答：

1. 这个类或函数负责什么；
2. 每个参数表示什么，调用者应传入什么；
3. 返回值表示什么，何时为空或失败；
4. 代码的主线路径怎样运行；
5. 哪些地方会提前返回、降级、重试、清理或改变状态；
6. 为什么关键实现不能简单地换成另一种写法。

## 强制语言规则

1. 注释和文档字符串以中文为主。
2. 函数名、类名、字段名、协议名、标准名、错误文本和代码标识符保留原文。
3. `Args`、`Returns`、`Raises`、`@param`、`@return` 等语言或工具约定标签可以保留英文，但说明正文必须主要使用中文。
4. 只有以下情况可以主要使用英文：
   - 仓库明确要求公共 API 文档只能使用英文；
   - 代码将被提交到要求英文注释的上游项目；
   - 自动化工具无法识别中文且会影响构建或文档生成。
5. 即使必须使用英文，也要优先保证语义完整，而不是省略注释。

# 一、符号级注释

## 1. 类、结构体、接口与模块

每个新增或修改的类、结构体、接口、协议、重要枚举和模块都必须有简介。

简介至少说明：

- 它代表什么或负责什么；
- 它位于哪一层；
- 它维护什么核心状态；
- 它与相邻组件的责任边界；
- 必要时说明生命周期、线程安全性或所有权。

不要只写：

```text
用户服务类。
```

应写成：

```text
负责读取和更新用户资料，并在写入数据库成功后刷新用户缓存。
该类不处理登录鉴权，调用者必须在进入本层前完成身份校验。
```

## 2. 函数与方法

每个新增或修改的函数、方法、构造函数、析构函数、回调函数和非平凡 lambda 都必须有一行或多行简介。

简介应优先描述：

- 对外职责；
- 输入到输出的语义；
- 关键副作用；
- 失败方式或重要边界。

不要把函数名机械翻译成中文。

差：

```text
获取用户。
```

好：

```text
根据用户 ID 查询当前有效的用户记录；已删除用户视为不存在。
```

## 3. 参数

必须逐一解释每个参数。

参数说明至少覆盖适用项：

- 业务含义；
- 类型无法表达的约束；
- 单位，如毫秒、字节、百分比；
- 合法范围；
- 是否允许为空、`None`、`null`；
- 是否会被函数修改；
- 所有权是否转移；
- 默认值代表什么；
- 集合元素或字典键值的结构；
- 回调函数在何时、以什么线程或协程上下文调用。

动态语言必须尤其注意：类型标注不能替代参数语义。

例如 `items: list[dict[str, object]]` 仍然应解释每个字典至少包含哪些字段、字段类型和缺失字段的处理方式。

## 4. 返回值

有返回值的函数必须解释返回值。

返回值说明至少覆盖适用项：

- 返回对象表示什么；
- `None`、空集合、零值或特殊值分别表示什么；
- 返回值是否为新对象、借用引用、内部缓存或共享对象；
- 调用者是否需要释放、关闭或确认；
- 多返回值中每一项的含义；
- 错误是否通过返回值、异常、状态码或全局状态表达。

无返回值时，如果函数存在重要副作用，应明确写明副作用。

## 5. 异常、错误与副作用

存在下列行为时必须说明：

- 可能抛出的异常；
- 可能返回的错误码；
- 文件、数据库、网络或缓存写入；
- 修改传入对象；
- 修改全局状态；
- 获取锁、阻塞、重试或等待；
- 启动线程、协程、子进程或后台任务；
- 提交或回滚事务。

不需要列出实现上理论可能发生的所有底层异常，只记录调用者需要据此处理的稳定行为。

# 二、函数体关键路径注释

函数体内不要求逐行注释，但关键路径必须有注释。

## 1. 短路与守卫路径

在提前返回、快速失败、缓存命中、幂等跳过、空输入处理等位置说明：

- 为什么可以提前结束；
- 这个分支保护什么不变量；
- 返回值或状态代表什么。

示例：

```python
# 缓存中已经存在最终结果时直接返回，避免重复请求下游服务。
if cached_result is not None:
    return cached_result
```

## 2. 主线路径

当函数包含多个阶段时，用注释标出主线阶段，而不是让读者从细节中猜流程。

例如：

```text
1. 校验并规范化输入；
2. 批量读取依赖数据；
3. 执行核心计算；
4. 持久化结果；
5. 更新缓存或发布事件。
```

阶段注释应描述意图，不要复述紧随其后的单行代码。

## 3. 失败、降级与恢复路径

以下路径必须解释原因和语义：

- fallback；
- retry；
- timeout；
- circuit breaker；
- rollback；
- cleanup；
- partial failure；
- dead-letter；
- 忽略特定错误；
- 返回旧数据或默认值。

尤其要说明“为什么这里允许继续”或“为什么这里必须停止”。

## 4. 状态机与协议路径

涉及状态迁移、网络协议、消息顺序、事务阶段、调度策略时，应在关键分支说明：

- 当前状态；
- 触发条件；
- 迁移后的状态；
- 必须维持的顺序或不变量。

## 5. 并发与异步路径

涉及锁、原子变量、协程、线程、队列、回调或异步任务时，应说明：

- 哪些数据受保护；
- 锁的获取顺序；
- 为什么不能缩小或扩大临界区；
- 回调在哪个执行上下文触发；
- 取消、超时和关闭如何传播；
- 是否允许并发调用。

## 6. 性能敏感路径

出现批处理、零拷贝、缓存、对象池、延迟初始化、内存复用、索引选择等非直观实现时，应解释：

- 当前写法优化什么；
- 避免了什么开销；
- 付出了什么可维护性或内存代价；
- 哪个数据规模下该选择才有意义。

## 7. 反直觉代码与兼容逻辑

以下代码必须说明“为什么”：

- 看似多余但不能删除的判断；
- 为兼容旧格式保留的分支；
- 对编译器、运行时或第三方库缺陷的规避；
- 特殊平台处理；
- 与外部系统约定不一致的映射；
- 故意不使用更常见写法的实现。

如有稳定外部依据，可在注释中引用 Issue、标准章节或文档标识，但不要粘贴长链接说明。

# 三、语言落地规则

优先遵守仓库已有注释格式；仓库没有明确格式时使用以下默认规则。

## Python

- 类、函数和方法使用 docstring；
- 优先保留或采用仓库现有的 Google、NumPy 或 Sphinx 风格；
- 动态结构必须描述字段、元素类型、可空性和约束；
- `Args`、`Returns`、`Raises` 标签可使用英文，正文使用中文；
- 函数体关键路径使用 `#` 中文注释。

```python
def load_user(user_id: int, include_deleted: bool = False) -> User | None:
    """根据用户 ID 加载用户记录。

    Args:
        user_id: 用户唯一标识，必须为正整数。
        include_deleted: 是否允许返回已软删除的记录。

    Returns:
        找到时返回用户对象；不存在或不允许返回已删除记录时返回 None。
    """
```

## C / C++

- 公共与私有类、结构体、函数和方法均使用 `///` 或 `/** ... */`；
- 参数使用 `@param`，返回值使用 `@return`；
- 指针和引用参数说明可空性、所有权、生命周期和是否被修改；
- RAII、锁、移动语义、内存布局和 ABI 相关代码说明关键约束。

```cpp
/// 根据任务 ID 查找仍处于运行状态的任务。
///
/// @param task_id 任务唯一标识，必须大于 0。
/// @return 找到时返回任务的只读指针；不存在时返回 nullptr，所有权仍归调度器。
const Task* FindRunningTask(std::uint64_t task_id) const;
```

## Go

- 导出符号注释必须以符号名开头，以满足 Go 文档约定；
- 未导出的函数和方法也必须说明职责；
- `context.Context` 参数说明取消和超时语义；
- channel、goroutine 和所有权转移必须说明关闭方和生命周期。

```go
// LoadUser 根据用户 ID 查询当前有效的用户记录。
// id 必须大于 0；找不到记录时返回 (nil, nil)。
// ctx 取消后应尽快终止数据库查询并返回 ctx.Err()。
func LoadUser(ctx context.Context, id int64) (*User, error)
```

## Rust

- 使用 `///` 或 `//!`；
- 根据需要包含 `# Arguments`、`# Returns`、`# Errors`、`# Panics` 和 `# Safety`；
- 对借用、生命周期、所有权转移和 `unsafe` 不变量进行说明。

## Java / Kotlin / C#

- 使用语言标准文档注释：Javadoc、KDoc 或 XML documentation；
- 逐一说明参数、返回值、异常和可空性；
- 异步方法说明取消、线程切换和副作用。

## JavaScript / TypeScript

- 使用 JSDoc 或 TSDoc；
- 即使 TypeScript 已有类型，也要说明业务语义、可空条件和对象字段约束；
- Promise 返回值说明 resolve 与 reject 的条件；
- 回调说明调用时机和调用次数。

## Shell / PowerShell

- 脚本顶部说明用途、输入、输出、依赖和副作用；
- 每个函数说明参数、标准输出、标准错误和退出码；
- 危险命令、清理动作、权限变化和幂等判断必须有注释；
- PowerShell 优先使用 comment-based help。

## SQL

- 存储函数、过程和触发器说明输入、返回值、副作用和事务边界；
- 复杂 CTE、锁、隔离级别、去重策略和非显然索引假设应有注释；
- 不要给每个简单 `SELECT` 字段写同义注释。

# 四、注释质量边界

## 注释应解释什么

优先解释：

- 责任；
- 业务语义；
- 约束；
- 不变量；
- 状态变化；
- 失败语义；
- 关键取舍；
- 反直觉原因。

## 注释不应解释什么

不要机械解释代码字面含义。

差：

```python
# 将 i 加 1
i += 1
```

好：

```python
# 跳过已经确认的连续序号，下次从第一个缺口继续扫描。
i += 1
```

## 禁止事项

- 禁止用函数名改写一遍作为唯一注释；
- 禁止留下 `TODO: add comment` 等占位文本；
- 禁止写与实现不一致的过期注释；
- 禁止虚构性能原因、协议要求或历史背景；
- 禁止为了满足数量要求给每行代码加噪声；
- 禁止使用“这里做一些处理”“正常逻辑”等空洞描述；
- 禁止只给公共函数写注释而忽略复杂私有函数；
- 禁止在动态语言中只写类型、不写数据语义。

# 五、修改已有代码时的范围

1. 所有新增符号必须符合本规范。
2. 所有被修改的类、函数和方法必须同步检查并更新注释。
3. 修改了参数、返回值、异常、副作用或关键流程时，必须同步修改原注释。
4. 当一个文件由本次任务整体生成或重写时，该文件内所有类和函数都必须符合本规范。
5. 不要为了补注释无限扩大到完全无关的历史文件；但若当前修改依赖附近缺失注释的复杂私有函数，应在同一任务内补齐。
6. 生成代码、第三方 vendored 代码、快照和锁文件不应手工修改；应修改生成源、模板或生成器，并在必要时说明限制。

# 六、编码前执行流程

每次编写代码前按以下顺序执行：

1. 读取仓库根目录和目标目录的 `AGENTS.md`、`CONTRIBUTING.md`、README、语言规范及现有代码风格；
2. 读取本 Skill；
3. 确认本次将新增或修改的类、函数、方法、脚本入口和关键 SQL；
4. 选择与仓库一致的文档注释格式；
5. 在写实现的同时完成符号级注释，不要最后临时补一句；
6. 在短路、主线、错误、状态、并发和性能关键路径补充必要注释；
7. 运行格式化、静态检查、构建和测试；
8. 交付前执行下方检查表。

# 七、交付前强制检查

在提交代码、输出补丁或回复用户前逐项确认：

- [ ] 每个新增或修改的类、结构体、接口和重要枚举都有职责简介；
- [ ] 每个新增或修改的函数、方法、构造函数、析构函数和重要回调都有简介；
- [ ] 每个参数都说明了业务含义和必要约束；
- [ ] 每个返回值都说明了语义以及空值、错误或所有权边界；
- [ ] 重要异常、错误码和副作用已经说明；
- [ ] 短路路径、主线路径、失败恢复路径和反直觉代码已有必要注释；
- [ ] 并发、状态机、协议和性能敏感逻辑说明了关键不变量或取舍；
- [ ] 注释主要使用中文；
- [ ] 注释与当前实现一致，没有复制旧描述；
- [ ] 没有用逐行同义翻译制造噪声；
- [ ] 动态语言的数据结构、字段和可空性已经讲清楚；
- [ ] 格式化、文档检查、静态检查、构建和测试结果如实记录。

任何一项不满足时，不应把代码视为完成。
