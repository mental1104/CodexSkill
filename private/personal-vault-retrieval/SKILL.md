# 私人知识库检索规范

## 定位

这是查询用户私人 Obsidian 知识库时的强制 Skill。

知识库位置：

- Repo：`mental1104/Obsidian`
- Branch：`main`

本 Skill 负责：

1. 判断当前请求是否需要查询私人知识库；
2. 使用 GitHub 工具检索相关笔记；
3. 从路径、标题、正文、frontmatter 和双链中判断证据质量；
4. 处理多个笔记之间的重复、演进和冲突；
5. 基于私人笔记回答问题，同时明确区分原始结论、推断和新建议；
6. 避免泄露与当前问题无关的私人内容。

本 Skill 只负责知识库检索和基于检索结果的回答，不负责将新内容归档回知识库。需要创建或重写 Obsidian 笔记时，应继续进入归档 Router。

# 一、强制触发条件

当用户询问以下任意内容时，必须在回答前读取并应用本 Skill：

- “我的知识库”；
- “我的笔记”；
- “之前归档”；
- “查一下 vault”；
- “从笔记里找”；
- “之前那个实验”；
- “之前的文档”；
- “之前的结论”；
- 个人学习记录、项目文档、源码阅读记录；
- 已归档的实验、benchmark、pprof、trace 或排障结论；
- 个人技术路线、任务、计划和 Roadmap；
- 需要以用户历史记录为依据继续讨论或做决策的请求；
- 等价的私人知识库查询请求。

如果用户只是在讨论通用知识，不要为了“可能有相关笔记”而主动扫描整个知识库。

只有当私人记录会实质影响答案、用户明确要求查笔记，或当前问题明显依赖其历史实验和决策时才触发。

# 二、来源优先级

## 1. 私人仓库优先

查询知识库时：

1. 优先使用 GitHub connector 或其他已连接的私有仓库工具；
2. 不使用公开 Web 搜索替代对私人仓库的访问；
3. 不根据聊天记忆伪装成已经读取了仓库；
4. 不根据文件名、旧回答或可能存在的内容猜测笔记结论。

公开 Web 可以用于补充最新外部事实，但不能被描述为私人知识库证据。

## 2. 技术实验以 Vault 为事实源

对于以下用户亲自完成或归档的内容，应把 Vault 作为主要事实来源：

- benchmark 和性能数据；
- pprof、trace、火焰图和 profiling 结论；
- Redis、数据库、网络、消息系统等实验；
- 项目设计文档和实现路线；
- 已执行的命令、测试结果和验证记录；
- 已归档任务、计划和 Roadmap；
- 源码阅读记录和代码走读结论。

不要用通用经验覆盖用户已经记录的真实实验结果。

# 三、检索流程

## 1. 明确检索目标

开始搜索前，从当前请求中提取：

- 核心主题；
- 精确名称、路径、类名、模块名、协议名或实验名；
- 用户希望得到的是结论、原始证据、操作步骤、历史过程还是当前任务状态；
- 是否有时间范围、版本、分支或项目范围；
- 哪些私人内容与当前问题无关，不应检索或展示。

除非歧义会导致搜索完全不同的主题，否则直接检索，不要先要求用户补充大量信息。

## 2. 搜索顺序

按照以下顺序逐步扩大搜索范围：

1. 精确关键词；
2. 精确短语和完整技术名；
3. 文件名、目录名、类名、函数名、错误文本；
4. 中文同义词；
5. 英文或缩写变体；
6. 相关技术术语、上位概念和常见别名；
7. 可能的前置文档、后续文档和双链目标。

示例：

```text
Redis 主从复制
→ replication
→ INFO replication
→ master_replid / master_repl_offset
→ 相关实验目录和双链
```

不要第一步就使用过宽关键词，否则容易混入无关私人内容。

## 3. 判断相关性

评估检索结果时综合考虑：

- 文件路径和目录语义；
- 文件名；
- YAML frontmatter；
- 一级和二级标题；
- 正文上下文；
- 双链与反向关系；
- 是否包含用户询问的版本、时间、环境或实验条件；
- 是否为草稿、过程记录、最终结论、操作手册或已废弃方案。

不要只因为某个关键词出现过，就把整个文档视为可靠答案。

## 4. 必要时展开文件

搜索摘要不足以支持答案时，应继续打开高相关文件，读取：

- 结论所在段落；
- 实验条件和输入；
- 原始命令或指标；
- 限制条件；
- 相关双链文档；
- 文档结尾的最终状态或后续更新。

对表格、图片、截图、PDF 或幻灯片中的关键证据，必须使用支持视觉内容的读取方式，不要仅依赖文本摘要。

# 四、笔记冲突与版本判断

当多个笔记存在冲突时，按以下顺序判断：

1. 用户明确指定的文件、实验或版本；
2. 内容中明确标注为最终结论、已验证、归档、完成或替代旧方案的笔记；
3. 更新且包含完整证据的笔记；
4. 与当前环境、版本和输入条件更匹配的笔记；
5. 原始实验数据和可复现证据；
6. 普通随手记录、草稿或未验证推测。

创建时间和修改时间只能作为辅助信号，不能单独证明内容更新。

如果无法确认哪一个结论有效，应明确呈现冲突：

```markdown
- 较早笔记认为：……
- 较新笔记认为：……
- 当前无法确认：……
```

不得静默选择一个看起来更合理的结论。

# 五、回答组织

## 1. 先给直接答案

默认先回答用户真正询问的问题，再补充笔记依据。

简单问题不需要输出完整检索过程；复杂问题可按以下结构：

```markdown
## 结论

<直接回答>

## Vault 依据

- `<路径>`：<支持的结论或证据>

## 判断边界

- <限制、冲突或缺失证据>
```

## 2. 区分三种信息

回答中必须区分：

### Vault 明确结论

笔记直接写明或由原始证据直接支持的内容。

表述示例：

```text
Vault 中的结论是……
```

### 基于 Vault 的推断

笔记没有直接写出，但可以根据多个记录合理推导。

表述示例：

```text
结合这些记录，我的推断是……
```

### 助手建议

基于当前问题提出、但并非笔记原有内容的新建议。

表述示例：

```text
在现有记录之外，我建议……
```

不得把助手建议伪装成用户以前已经确认的结论。

## 3. 引用文件路径

回答应尽可能注明相关路径，例如：

```text
Atlas/300-Database/Redis/主从复制实验.md
```

路径应来自真实检索结果，不得猜测。

如果工具支持行号或可点击引用，应同时提供引用。

# 六、隐私边界

1. 只检索和展示与当前请求直接相关的私人内容；
2. 不主动展开无关的财务、健康、关系、身份或其他敏感记录；
3. 不因为同一文档中存在无关私人信息就一并总结；
4. 用户询问某个项目时，不暴露其他项目的私有实现细节；
5. 不在公开 Web 搜索中提交私人仓库内容、文件路径、日志或密钥；
6. 发现凭据、Token、Cookie、密码、私钥或敏感配置时，不在回答中原样展示；
7. 只引用回答所需的最小必要内容。

# 七、访问失败与证据不足

## 1. 无法访问仓库

如果当前会话无法访问 `mental1104/Obsidian`：

1. 明确说明本次无法读取私人 Vault；
2. 不得假装已经检索；
3. 可以继续提供基于当前聊天和通用知识的最佳答案；
4. 明确标注该答案“不基于 Vault”。

推荐表述：

```text
当前会话无法访问你的私人 Vault。下面的判断仅基于本轮上下文，不是对已归档笔记的复述。
```

## 2. 没有找到相关笔记

经过精确词、同义词和中英文变体检索仍未找到时：

- 明确说明没有找到；
- 简要说明搜索过的主题范围；
- 不得创建虚构路径或补写不存在的结论；
- 可以给出不依赖 Vault 的建议，但必须与检索结果分开。

## 3. 证据不完整

只有标题、摘要或零散片段时，应说明证据范围：

```text
目前只找到一段过程记录，没有发现最终结论。
```

不要把过程记录自动升级为用户已经确认的长期决定。

# 八、与其他 Skill 的组合

- 用户要求查询已有笔记：使用本 Skill；
- 用户要求把当前内容写回 Vault：使用归档 Router；
- 用户先查询旧结论，再要求更新归档：先使用本 Skill 获取证据，再进入归档 Router；
- 查询代码实验后要求修改代码：本 Skill 负责检索历史证据，编码任务同时加载 `code-comment-writing`；
- 查询笔记后要求生成 Issue 或 PR：本 Skill 提供历史背景，最终产物继续加载对应 GitHub Skill。

# 九、交付前检查

回答前逐项确认：

- [ ] 当前请求确实需要私人知识库，而不是普通通用问答；
- [ ] 已优先使用私有 GitHub 工具，而不是公开 Web 替代；
- [ ] 搜索从精确关键词逐步扩展，而不是一开始全库泛搜；
- [ ] 关键结论已经打开原文确认，而不是只看搜索摘要；
- [ ] 已根据路径、标题、frontmatter、正文和双链判断相关性；
- [ ] 冲突笔记已经按证据和版本状态处理；
- [ ] 已区分 Vault 结论、基于 Vault 的推断和助手建议；
- [ ] 所有路径和结论都来自真实检索结果；
- [ ] 没有暴露无关私人内容或敏感凭据；
- [ ] 访问失败或证据不足时已经明确说明；
- [ ] 没有把公开 Web 内容伪装成私人知识库内容。

任何一项不满足时，不应声称答案已经由私人 Vault 支持。
