## 执行方式与证据

在已正常配置默认编码 Skill 的独立会话中，分别提交下面两个自然语言任务。给被测会话提供任务和实际项目材料，不把本文件的观察项作为答案提示；Skill 自己链接的相关案例仍可正常读取。

有现成项目时在隔离副本上执行并检查改动；没有项目材料时可以先做设计评估，但必须标为“设计评估”，不能声称构建或行为测试通过。本文件定义任务，不记录已通过的实测结果。

实测记录：[2026-11-08 新旧版本独立设计评测](results/2026-11-08-design-judgment.md)，包含六题十二次答复、匿名评审与公共入口编译探针；其设计评测结论不替代项目构建或运行结果。

## 主场景：多后端配置组件

### 自然语言任务

请审查一个 C++ 配置组件的模块组织。它提供文本载入、文本导出、对象字段查询和数组遍历，已经接入两个第三方解析库；应用只使用统一接口。

目前每个结果类型、节点类型、读取工具、解析器和后端各有一个公共头文件，阅读一次完整用法需要跳转多处。请提出更容易使用和维护的组织方式，并说明新增第三个后端时要改哪些部分。可以调整内部结构，不要求保留当前文件数量；不要扩展现有功能。

### 应观察的结果

- 公共入口围绕编解码与访问职责收敛，允许根据真实依赖采用其他同样清楚的划分。
- 后端私有细节可以分别维护，普通调用者无需接触第三方类型或内部目录。
- 能说明增加后端影响的范围，不以全部合成一个文件或每个类型都拆文件作为目标。
- 使用最小完整流程检验接口，并建议让该用法进入可执行测试；不强制改变既有测试顺序。
- 必要的资源与错误说明靠近相应实现或接口，用法放在测试或 README；不新增平行维护的 prompt 快照。

### 失败信号

仅机械减少文件；强制固定文件名或文件数量；为未要求的插件系统加入 registry；把原生后端类型暴露给普通使用者；为了目录一致性扩大到无关模块。

## 反向场景：小型稳定组件

### 自然语言任务

现有一个几十行的 C++ 配置读取组件，只有一个后端，没有替换后端的需求；公共接口和内部实现已清楚分开，测试使用项目既有布局。请审查是否需要进一步拆文件，并说明依据。这次只做审查。

### 应观察的结果

允许保持现有组织；不预建继承、注册、detail 目录或强制两模块结构；不修改代码。若确有问题，应指出当前具体的维护成本，而非套用多后端案例。

## 判定与记录

补充任务：现有 C++ 或 Python 端到端用例把 Docker 命令、进程等待、JSON 和业务断言混在一起；用户主要想读成功场景，并用另一份 demo 学会实际协议对接。请在保留行为的前提下整理阅读入口。

应观察：用例正文能直接看见请求、动作与领域断言，底层管理进程与报告转换；demo 仍显示真实端点、请求类型/关键字段、进度和结果，不只留下万能包装调用。小型清楚用例或专门教学 Docker 的示例作为反例，不强行隐藏其主题或创建适配框架。

同时检查主场景与反向场景。记录使用的 Skill revision、实际输入、项目材料、输出或 diff、已执行的检查与未验证部分。
