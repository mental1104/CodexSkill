# 服务接入与注册表案例

以下用任务导出服务说明判断方法。调用链和表格是关系示意，不规定具体框架、符号名称或文件布局。

## 案例一：生产接线

### 原问题与改进

需求是“让现有服务在生产启动时注册导出路由”。第一版新增了注册端口、路由定义和说明文档，临时 demo 也能调用，但真实应用仍没有创建端点或执行注册。

```text
第一版：
应用启动 → 旧组件 → 正常运行
文档示例 / 临时 demo → 新注册端口 → 新路由

接入后：
应用启动 → 构造现有业务服务 → 注入端点依赖
         → 注册路由与处理器 → 启动监听
请求到达 → 已注册端点 → 现有业务执行 API → 响应
应用退出 → 停止接收请求 → 按依赖关系等待或取消工作 → 释放资源
```

变化的关键是生产调用路径确实可达，新增接口和纳入构建只覆盖其中一部分。验证应检查真实启动入口调用了谁、业务服务注入到了哪里，并按本轮授权确认请求能否到达；没有整进程运行条件时，说明已经核实的接线和仍缺的运行证据。

执行适配器同理：实现 `新适配器 → 旧执行 API` 只证明适配关系。若需求包含生产接入，还要有 `生产调用方 → 新适配器`，不能因为适配器自身测试通过就宣称调用方已经切换。

### 条件改变时

- 用户只要求定义注册契约或以一个 health 端点验证框架，可以停在该阶段，并说明其余业务未接入。
- 新增能力只是公共库供未来调用方使用，本轮没有应用接入要求，不凭空创建服务器或启动入口。
- 用户只让阅读代码或讨论设计，只交付调用链和缺口，不据此修改或启动应用。

## 案例二：注册表的现场可读性

### 原问题与改进

同一张表里的方法和路径被移到另一份端点常量表，每个常量只用一次。排查一个真实请求时，需要反复跳转才能对应 handler。

| 位置 | 原写法 | 改进后的表达 |
|---|---|---|
| 公共部分 | 前缀与全部端点定义集中在另一处 | 公共前缀 `/api/v1`、资源片段 `/exports` 仍集中维护 |
| 健康端点 | `kHealthEndpoint → handler`，再跳转找方法和路径 | `GET + /health → HealthHandler` |
| 提交端点 | `kPrepareEndpoint → handler`，再跳转 | `POST + 资源片段 + /prepare → PrepareHandler` |
| 查询端点 | `kProbeEndpoint → handler`，再跳转 | `GET + 资源片段 + /{task_id} → ProbeHandler` |

公共前缀可由已有分组机制统一添加，每行就地写明方法、剩余路径和处理器。这样调整共同路径仍只改一处，排障时也能直接找到请求对应的注册项。

用户进一步要求“更平整”时，比较的是调用处需要理解的嵌套：

```text
原初始化：{{方法, 路径, 匹配方式}, 处理器}
简化后：  {方法, 路径, 处理器, 匹配方式}
```

可以由现有具名绑定类型的简洁构造承接，内部继续以 `.route`、`.handler` 表达职责；无需把内部所有读取改为 `get<0>`、`get<1>`。具体 C++ 构造与参数规则由 `cpp-code-style` 约束，这里不要求某个固定构造签名。

### 条件改变时

- 同一端点定义被客户端、服务端或文档生成器共享时，保留该共同契约，避免复制出不一致的路径。
- 当前初始化已经足够直观时，不为套用案例新增构造、工厂或另一层包装。
- 一次性局部 tuple 没有稳定字段职责时仍可使用；本例不构成 tuple 禁令。

## 案例三：发现与连接分开变化

需求明确要求：局域网和互联网采用不同方式按设备身份发现地址，但实际连接始终使用统一的 IP 和端口。若业务入口直接持有某个具体发现器并在内部创建传输实现，增加发现方式就会牵动建连流程。

```text
耦合写法：业务入口 → 具体 mDNS 实现 → 直接构造 TCP 连接

稳定边界：设备身份 → 已有发现端口 → 统一的控制 endpoint → 连接端口
                  ↑
          按需求装配不同发现实现
```

优先复用或收敛已有发现与连接契约。连接层只接收它需要的控制地址，数据传输层只接收自己的数据面参数；发现来源、选择策略和实际选中结果在确有需要时分别建模。不同发现方式不要求不同的业务入口，也不要求连接器识别设备 SN 或具体发现协议。

这里只为已提出的替换需求明确边界，不预建未定义的云 API、插件系统或空实现。缓存及失效重试沿用已确认语义，不因为抽出了接口就新增重试次数或回退行为。只有单个固定后端且没有替换需求时，直接组合也可以更自然。

验证时先运行受影响的发现/连接契约检查；当调用链、构建配置或进程装配变化时，再回归相应集成场景。若当前版本已通过完整检查且没有新改动，恢复上下文不构成重跑一整套的理由；仓库明确要求的最终回归仍须完成。

## 回放检查

把“任务导出”换成另一种业务：检查是否仍能区分能力定义与应用接入，并在保留真实共享契约的前提下减少跳转。只要求契约或已有跨模块共享端点时，不应照搬完整生产接线或删除常量。发现与连接案例应能迁移到其他明确存在多种发现来源的任务，不能演变成所有小组件都要建立工厂和继承体系。
