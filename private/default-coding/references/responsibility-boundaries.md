# 案例一：职责边界

适用于公共组件被按类型拆得过散，或需要在公共职责与私有后端之间选择文件边界的情况。

## 场景与证据

common 的 C++ JSON 组件需要用统一接口接入多个后端，提供编解码和节点访问。

第一版按 parser、document、value、reader 等类型分别拆文件。用户指出“当前拆得太散了”，要求按“序列化/反序列化”和“访问 json 对象”划分。随后又要求具体 JSON 实现分文件放在内部 detail 目录，因为外层不会直接与它们交互。

来源：code_style_1.md 第 13640、28742 行的用户反馈。这里只保留决策摘要，不依赖原始对话才能理解。

## 收敛后的判断

公共模块围绕调用方的职责组织：编解码与对象访问各有清楚入口。私有模块围绕变化来源组织：每个后端集中维护其原生资源、节点访问与编解码细节，第三方类型留在内部。

两次反馈指向不同边界。文件总数不是判断目标；要看调用方需要理解多少概念，以及更换一个后端需要同步多少位置。

## 条件改变时

- 单个后端且逻辑很小，可以留在一个文件；不为复制此案例预建 detail 目录或继承体系。
- 独立类型有真实复用或维护边界时，可以单独拆分，不要求所有类型挤进两个文件。
- 已发布的头文件或目录存在兼容契约时，先遵守迁移约束，不直接删除。
- 私有 detail namespace 可以保留；需要避免的是强迫普通调用者接触内部层级。

## 回归观察

用不同组件名称和后端重新提出问题，观察是否仍按职责与变化边界作判断，而非复刻 JSON 文件名或固定文件数量。任务与反向场景见 [职责边界回归](../evals/responsibility-boundaries-regression.md)。
