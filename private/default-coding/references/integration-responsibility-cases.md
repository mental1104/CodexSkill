# 接入职责案例

适用于 C++ / Python。以下划分表达职责和依赖方向，不规定固定层数、类名或目录数量。

## 案例一：业务适配、JSON 编码与持久队列

第一版“设备离线存储”同时校验具体业务 method、解析字段、编码 JSON、管理段文件与确认游标。用户需要通用队列时，只把类改名或换一个 JSON 解析库，都不能解除这种耦合。

```text
业务适配：领域消息 ↔ 既有 JSON 编码契约，负责业务校验与业务统计
JSONL codec：JSON 值 ↔ 合法单行文本，复用已有 JSON 库
文本队列：追加 / 查看队首 / 确认 / 恢复 / 容量与顺序策略
文件持久化：目录锁 / 段扫描 / 完整行读取 / 追加回滚 / 截尾 / 游标提交
```

当 JSON 与存储确需独立变化时，队列接收约定的单行文本，不理解业务 method、设备字段或 JSON 对象类型。编码器不做文件操作，业务层不操作段偏移。文件细节已妨碍队列策略阅读时，可收进内部持久化类；调用方仍使用简单队列接口。

先用 `getline` 和项目已有 JSON 库完成行读取/解析，不为 JSONL 发明第二套 JSON parser。崩溃尾行、确认凭据和轮转是持久队列的真实职责，不能因为用了库就省去。部署目录从既有配置体系传入，通用头文件不硬编码机器专属路径；目录为空等失败规则沿用项目契约。

编码器与队列可以是同一对文件里的两个类，内部文件能力也不必成为公共模块。优先复用已有目录；仅有一个类不构成新建业务目录的理由。测试分别验证编解码、真实文件队列与业务适配，不让通用队列测试必须构造某种设备事件。

反向情形：只需一段简单追加日志时，不提前搭建可替换持久化后端；通用 JSON 队列若不要求格式独立，也不必强制改成字符串 API。原接口已经发布时先处理迁移约束。

## 案例二：策略拥有产品差异，主链路管理生命周期

多个产品的输入来源不同，但输出 MQTT 契约统一。第一版把产品配置与专属队列塞进公共组件构造函数，随后换成 `ConfigureFeature()`；主流程仍理解该业务，新增框架组件又引入第二套生命周期。

```text
未解除的耦合：主流程 → SupportsFeature → 解析专属配置 → 创建专属服务

按已有扩展点接入：产品策略 → 选择源适配、解析专属配置、创建所需服务
                 主流程 → 通用持有、启动、失败回收、停止
                 源适配 → 统一领域样本 → 公共上报服务 → 固定输出协议
```

复用已有产品注册和服务/定时任务机制，让输入差异止于源适配器。仅把型号判断改成能力 Boolean，后面仍创建业务对象，不算完成边界调整。普通服务已经能承担职责时，不为规避一个构造参数新增框架 Component 或全局单例。确需独立服务生命周期时说明当前原因；已有调度能完成时，不再建平行服务列表接口。

只支持少数产品的局部工厂，表达它自己的支持集合即可；无关产品统一按现有契约拒绝，新增无关枚举不应迫使它和测试逐项追加分支。新增被支持的产品才补映射和相应行为测试。

反向情形：领域状态机需要穷尽处理整个枚举时，保留穷尽检查，不为减少修改加入吞掉新状态的 `default`。只有一个固定产品、尚无变化需求时，可直接组合；不因本例提前建立策略体系。
