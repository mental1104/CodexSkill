# 业务场景与对接示例

本案例适用于 C++ / Python。以下为阅读顺序与职责示意，不是已运行代码，也不规定目录名或类层次数量。

## 案例一：先读懂场景，再按需展开容器机制

第一版把部署命令、进程等待、JSON 下标、故障注入与业务断言平铺在用例中。即使后来把它们搬进一个大函数，读者仍需通读基础设施才能回答“本用例证明什么”。

```text
平铺：拼 Docker 命令 → 启进程 → 解析 JSON → 拼另一命令 → 检查零散字段

阅读入口：请求（路由、数据、目标） → 完成一次应用交互 → 对结果证据作业务断言
按需展开：应用会话（等待接收者就绪、发送、收集双方结果）
         → 容器与进程适配（命令、超时、日志、回收、报告解码）

直连成功用例：TransferRequest（route=LAN、8 MiB、目标设备）
             → fixture.Transfer(request)
             → TransferEvidence：实际路由为 LAN、双方成功、接收文件大小/摘要一致
```

场景使用带字段语义的请求和证据，直接保留预期路径、成功/失败及产物条件，基础设施将原始报告转换后再交给它。可优先复用现有 fixture 的具名方法；只有机制已经反复妨碍阅读或确有替换需求时才增加独立适配接口。不为摆脱一个命令字符串预建环境插件框架。

此处只决定代码可读性边界。应用是否独立部署、云路径是否真隔离，另按适用的 `service-blackbox-validation` 核实；清楚的函数名不能替代这些证据。

反向情形：一个十几行、已有明确断言的简单测试，可以保持原样。不要把主要业务动作与期望也抽成无法理解的 `RunScenario(id)`。

## 案例二：对接指南的主流程保留真实协议

需求是读两份示例就会调用服务。把生产者缩成 `run_producer(args)`、消费者缩成 `run_consumer(args)` 虽然行数少，却把学习目标藏进公共模块。

```text
生产者主流程：准备源数据 → 选择实际公开端点和接口类型
              → 填写关键请求字段 → 提交并传入具名进度回调 → 判断最终结果
消费者主流程：按约定等待完成通知 → 独立读取产物 → 核对大小/摘要 → 输出结果位置
基础设施：参数解析、运行时初始化与释放、传输编码、日志与异常的共同行为
```

接口名可来自参数，但在调用处或紧邻说明中写清默认端点、协议类型及其来源；异步协议说明请求、反馈和最终结果分别是什么。使用项目真实客户端和生成类型，辅助函数负责等待等机制，不替换公开调用契约。数据目录、源文件与目标路径的映射须与实际部署一致。

Python 示例在用户要求时可用装饰器统一日志和异常，具体类型与失败语义由 `python-code-style` 维护。错误处理不能让失败看起来成功，进度回调仍要读得见。

反向情形：若本轮示例要教学的就是容器启动或协议编码，该机制本身便是主流程，不应隐藏。普通库的最小用法也不必创建生产者/消费者或另写一套 CLI。
