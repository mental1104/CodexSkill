# 队列隔离与资源预算

适用于用户明确要求一类任务不能挤占另一类任务容量的 C++ / Python 调度修改。以下是设计推演，不代表某个服务已经实现或运行通过。

## 先确定隔离的是哪一种资源

假设后台任务固定 2 个执行额度，客户下载固定 5 个发送额度，双方不借用。先沿每条生产入口检查预算，不能只按配置名或协议名分类：

| 阶段 | 需要回答的问题 |
|---|---|
| 准入 | 客户请求是否因为后台的排队数、运行数或全局计数被拒绝？ |
| 等待 | 队列与等待容量是否按约定独立？后台未就绪的队首是否挡住客户任务？ |
| 执行与发送 | 哪些路径消耗同一种额度？中转、直下载或其他适配入口是否能绕过或重复计算？ |
| 释放 | 额度是否持有到实际工作结束？完成、失败、取消和连接断开是否都正确归还？ |

复用执行器、任务状态查询或取消机制可以保留，前提是共享机制不破坏约定的可执行容量。需要资源实例各自独立，还是只需分类记账和调度，由实际阻塞点决定；不强制为每个入口新建线程池。

## 从共享计数改为按资源归属记账

有缺口的处理：虽然建立了两个队列，客户准入仍读取“全部等待任务数”；后台排满后，客户自己的发送额度尚空闲也被拒绝。

符合固定隔离的处理：后台准入与执行只消耗后台预算，客户准入与发送只消耗客户预算。后台用满时客户仍可开始，客户用满时后台仍可开始；一方空闲也不会使另一方超过自己的硬上限。

如果中转下载和直下载最终占用的是同一种客户发送资源，5 个额度应覆盖两条路径的合计占用，不能各给 5 个后仍宣称客户总并发为 5。若准备线程、中转执行和文件发送本来是不同资源，可以各有预算，但必须说明各自限制什么，以及一项任务何时持有哪种额度，不能将阶段上限直接相加当作下载并发。

“客户不受后台挤占”也不代表客户永不失败。客户自身满载时，沿用已确认的拒绝、有限等待或背压契约；磁盘、网络等未纳入隔离承诺的共享资源仍需如实说明。需求没有改变全局安全上限时，也不能自行删除它；若它与固定容量保证确实冲突，指出具体约束再确定取舍。

## 用行为验证承诺

在已有授权内，用后台满载时发起客户请求、客户满载时发起后台请求，以及一方空闲时另一方超过自身上限的场景，验证互不挤占和禁止借用。覆盖实际消耗预算的入口，并在释放后重试，检查失败或取消没有泄漏额度。两个计数器、编译通过或旧测试数量都不能代替这些行为证据。

旧断言若明确要求共享容量，应指出它与新需求的冲突；区分尚待修改的旧契约与实现回归。测试修改仍遵守当前仓库授权，普通隔离需求不自动启动 TDD 阶段审批。通过公开服务协议验收时，组合 `service-blackbox-validation`；未运行的场景标为待验证。

## 条件改变时

- 需求只是客户优先，允许后台借用空闲容量时，可使用保底加共享的策略；不能套用固定分区而损失已要求的吞吐。
- 两类任务明确共用总预算时，保留总量约束，不因入口协议不同就拆成独占额度。
- 只读分析并发现象时，先核对配置与时间线，不直接改调度器或提高上限。
- 小型单队列没有隔离需求时，不预建多租户预算框架。
