# 上报契约与验证案例

适用于 C++ / Python 的缓存、批量上报与补传实现。数值和调用链仅说明判断方法，不规定消息系统、批次大小或统一的持久化策略。

## 案例一：可靠性要按层决定

需求允许“客户端接受请求后，最终送达失败的风险不追踪”，同时要求“已知离线或发送明确失败时落盘、恢复后补传”。第一版将前者理解为取消离线队列，后来又为防崩溃丢数据而把所有在线样本先写盘；两次都改变了原契约。

| 判断维度 | 这个案例已确定的要求 | 实现边界 |
|---|---|---|
| 批次触发 | 收到 N 条有效、未重复快照 | 计数触发，不能自动改成精确时钟周期 |
| 持久化时点 | 明确离线或本地发送失败 | 在线成功路径不产生持久化数据记录 |
| 删除确认 | 客户端已接受发送请求 | 按这个约定移除；不声称 broker 或云端落库已确认 |
| 丢失范围 | 在线内存批次崩溃、已接受后未送达允许丢失 | 不据此删掉离线补传，也不自行增加 write-ahead 队列 |

```text
在线：有效快照 → 内存累计 N 条 → 调用发送
      → 已接受：清空该批次
      → 明确失败：写入离线队列；写盘也失败时保留尚未转交的数据
离线：按约定将待发数据持久化 → 恢复后读取 → 发送被接受后确认移除
```

测试同时检查正负副作用：前 N−1 条在线样本无 JSONL 数据文件；第 N 条成功后仍无数据文件；离线或失败才有对应内容。锁文件、确认游标等管理文件与数据文件分开判断。测试应验证已知契约，不把后来擅自增加的行为写成新的通过标准。

反向情形：明确要求在线采样也能抗重启丢失时，逐样本持久化可能正是必要设计；要求 broker 或应用确认时，也不能只依据客户端接受就删除。不要为复制本例降低其他项目的可靠性。

## 案例二：上游节拍、补传和在线发送分别建模

上游每分钟产生一条快照，下游需求是累计 N 条后发送。下游不需要再建立一个精确的分钟采样器和十分钟发送器；实际到达间隔可以变化。重复、无效输入和来源重启时是否计数、是否提前结束旧批次，应来自协议约定，不能靠去重后的字段值猜测。

用户明确要求历史补传不阻塞在线发送，且已有启动/重连事件时，可采用一轮有界后台消费：

```text
启动或恢复连接 → 有积压且本轮消费未运行 → 启动一轮消费
清空 / 断连 / 发送失败 → 按约定结束，保留未确认数据
应用关闭 → 停止触发、结束并回收本轮工作
```

独立线程或两个队列本身不能证明互不阻塞。检查共享锁是否跨阻塞发送、客户端是否支持并发及关闭顺序；用历史发送被控制阻塞的场景，证明新满批次仍能执行所承诺的发送动作。已有执行器可以满足时直接复用，不强制新增线程。磁盘预算按整体约定计算，不因内部拆队列而翻倍，也不因此增加未要求的在线落盘。

反向情形：产品要求按墙钟定期发送不足 N 条的批次，仍须有对应定时机制；协议只允许串行或严格 FIFO 时，也不自行绕过顺序。独立消费不是所有补传任务的默认模式。

## 案例三：最小链路也要有可辨识的输入

只验证“上游消息 → 订阅转换 → 下游发布接口”时，可以用真实上游 Publisher 与记录型下游 fixture，沿实际业务链路捕获最终 Topic、选项及 payload；这只证明发布请求，不等于实际 broker 收到，也不自动要求硬件、容器或真实云平台。

映射用例若除序号外全为默认零值，即使每条都错误地使用了最后一帧，也可能通过。正常样本应完整且符合已知单位、枚举、质量状态和数值关系，例如：

| 输入身份 | 温度 | 电压 | 期望 |
|---|---|---|---|
| 快照 1、槽位 A | 21 | 4811 | 输出记录 1、槽位 A 保留各字段值 |
| 快照 1、槽位 B | 27 | 4922 | 与槽位 A 不串位 |
| 快照 2、槽位 A | 23 | 4833 | 与前一帧不同，不复用末帧或旧帧 |

按契约逐字段核对转换与最终序列化，另设真实零值、空字符串、缺失、`null` 和各质量维度的边界样本。某时间质量异常若不影响测量值，就不能把全部测量一并抹空。单设备必须空字符串等规则仅按该协议执行，不推广为所有标识字段的约定。

用户需要观察时输出本次输入与最终捕获结果，按 `code-comment-writing` 的观察日志规则组织。日志不能代替断言；反过来，通过摘要也不能替代用户明确要求的可见业务输出。

反向情形：计数或去重的局部测试可以只聚焦对应输入，零值本身合法时应保留零值测试；不把整个字段矩阵复制到每一个用例，也不为普通补测试引入 TDD 审批。
