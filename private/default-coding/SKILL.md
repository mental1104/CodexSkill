# 默认编码：工程判断与复杂度控制

版本：0.1.3

## 定位与适用范围

本 Skill 初期仅适用于 C++ 和 Python 的代码新增、修改、修复、重构和测试。混合语言任务只在 C++ / Python 部分应用，不对其他语言自动触发。

目标是正确满足当前需求，同时降低代码的长期理解和维护成本。优先减少**需要长期记住的概念与关系**，而非机械减少代码行数。

本 Skill 负责上层工程取舍，不重复 `cpp-code-style`、`python-code-style` 的语言级约束，也不替代 `code-comment-writing` 的注释要求。用户明确要求、仓库硬约束、公共 API / ABI / 协议契约和适用的专项 Skill 仍须遵守。激活 `tdd-workflow` 时，不得越过其阶段边界。

## 实现前：寻找自然的落点

1. 根据任务阅读相关入口、调用方、相邻实现与仓库约定；不为小修改遍历整个项目。
2. 确认当前真正需要满足的行为、限制和修改边界，区分实际需求与自己想象的未来需求。
3. 优先复用已有职责、数据流和抽象层级。能局部修改时，不为“设计更完整”另建平行机制。需求明确要求替换发现来源、保持建连契约稳定时，参考 [发现与连接案例](references/service-integration-cases.md#案例三发现与连接分开变化)。
4. 现有结构确实妨碍本次需求时可以调整，但只改变必要的部分，不顺手重构无关代码。
5. 新项目缺少现有模式时，从最直接、易读、可维护的结构开始，不预先搭建一套大架构。

涉及现有应用的路由注册、组件挂载或执行适配时，先找到真实启动入口和调用方。需求是让应用使用新能力时，完成条件应包含生产依赖装配、注册调用和必要的启停清理；声明、文档示例、临时 demo 或纳入构建不能证明生产路径已接通。用户已明确只做契约、框架验证或某一阶段时，按该范围交付，并在结果中直接指出生产调用方是否已经使用，避免把后续业务一并扩入。判断“提供能力”与“接入应用”的交付范围时，读 [生产接线案例](references/service-integration-cases.md#案例一生产接线)。

模块边界优先围绕调用方的使用职责组织；私有实现可以按后端、依赖或变化来源分别维护。不要机械地每个类型拆一个文件，也不要为减少文件而混合不同职责。需要判断“拆得太散”与“后端应独立维护”时，参考 [职责边界案例](references/responsibility-boundaries.md)。

涉及离线队列、重试或批量上报时，分别确认触发条件、持久化时点、发送成功标准和可接受的丢失范围。接受某一层故障风险不等于取消其他已要求的恢复能力；建议更强保障时先标为可选，不把逐样本落盘或更强确认悄悄加入实现。原要求及后续明确纠正共同决定当前行为，详见 [上报契约与验证案例](references/reporting-contract-cases.md)。

## 编码时：控制概念增量

- 默认选择能清楚表达意图并满足约束的直接实现。**抽象应降低整体理解成本，而不是增加层次来证明设计存在。**
- 新增类、接口、模块、状态、依赖、配置项或间接层前，确认它解决了当前真实的职责边界、重复、变化或复杂性问题；“将来可能扩展”本身不充分。
- 不默认使用工厂、策略、注册表、继承体系和通用框架；确实更自然时也不刻意回避。
- 不为追求短代码而合并不同职责、制造过长函数或取消有意义的抽象。
- 按真实变化边界隔离业务规则、通用机制和产品组装；把专属构造参数挪成 setter 不等于解耦。优先复用已有目录、策略和生命周期，普通内部类或服务足够时不新增框架组件。存储分层与产品适配的具体取舍见 [接入职责案例](references/integration-responsibility-cases.md)。
- 让主要数据流、状态变化、所有权、错误契约和副作用尽可能直接可见；常用操作不应要求调用方了解内部成员布局。避免重复状态、隐藏约定、不必要的 fallback、兼容分支和业务校验。
- 尊重已有契约。实际需要的兼容性、正确性、安全性、性能和资源管理约束优先于形式简洁，不因本 Skill 删除必要防护。
- 尊重项目已有风格，但不机械复制明显的遗留缺陷。
- 实现相关的必要解释靠近代码，公开用法放在测试或 README，重复执行的仓库规范集中维护；避免另存一套需要随实现同步的 prompt 或实现快照。注释形式遵循 `code-comment-writing`。

用户要通读业务用例或以 demo 学习对接时，让阅读入口直接表达业务请求、关键交互与结果期望，把 Docker、进程、命令拼接和报告编解码等机制收进按职责组织的下层。封装后仍须能看见本次要教学的公开端点、请求类型/关键字段、进度回调与结果处理；不能用一个万能 `run()` 把它们一起藏掉。已有结构很清楚时不增加层次。边界与反例见 [业务场景与对接示例](references/readable-client-scenarios.md)。

路由等声明式注册表应便于在注册位置直接对照外部请求排障：集中维护公共前缀和重复路径片段，每项就地写清方法、路径后缀与处理器。仅为单条记录取名的端点常量，若只增加跳转而没有复用收益，可以省去。用户要让初始化更平整时，优先在现有具名类型上提供必要的简洁构造，保留字段语义；不因举例提到 tuple 就把整套内部模型改成位置索引。已有跨模块复用或公共契约的端点定义仍应保留。具体对照见 [注册表案例](references/service-integration-cases.md#案例二注册表的现场可读性)。

### 排障日志同时检查信息与噪声

优化请求日志或处理“失败原因看不出来、轮询刷屏”时，沿本次请求的接收、业务处理和响应链路检查：

- 失败记录应能关联本次请求、还原必要输入并定位失败原因；在拥有上下文的层补足业务标识、解析后的资源和底层错误，异步回调延续关联标识。正文按现有规则脱敏、限制长度并转义，不能记录时说明原因；仅有状态码或笼统错误文字不足以完成排障目标。
- 对没有业务动作的正常高频 health / 心跳探测，默认静默，失败时保留诊断；只把逐次成功日志降到 DEBUG 仍可能刷屏。业务失败按已有契约判断，不能仅凭 HTTP 200 静默真实故障，也不把该策略扩大到所有成功业务、进度或审计事件。
- 公共请求与响应诊断在已有公共入口处理，业务原因留在相应职责层；端点差异优先沿用已有注册信息，不让通用后端按业务路径猜策略，也不为少数端点预建通用日志框架。日志等级、正文阈值及保留字段按仓库与本次需求确定。

具体前后对照、正文取舍和不适用边界见 [请求诊断与探测降噪案例](references/request-logging-cases.md)。仅改其他业务时，不据此扫描或重做全项目日志。

## 完成后：自主做减法审查

从原始需求重新审视改动，不为第一版设计辩护：

1. 新增的每个概念是否都有当前明确的存在理由？
2. 是否存在可删除或合并、却不损害职责清晰性的包装层、转发层、特殊分支、状态或配置？
3. 从最小完整用法检查接口：调用者是否需要了解内部成员、重复选择配置或记忆同义操作？在满足已有契约的前提下，能否减少这些知识和跳转？新增默认行为仍须有需求依据。
4. 如果不依赖当前方案重新设计，是否存在更自然、同样正确且容易维护的实现？
5. 简化后是否保留了必要的边界，并能通过相关测试验证？

发现明显更自然且同样可靠的方案，应主动修改代码。审查由 Codex 自行完成，不把理解冗余设计并证明其错误的责任交给用户。

## 自主执行与验证

- 常规工程决策自行完成，不强制预先提交完整设计，也不逐项向用户请求批准。
- 仅当关键歧义会明显改变外部行为，或需要改变公共契约、持久化数据等难以撤销的边界时，才提出必要问题或明确取舍。
- 按改动风险先运行受影响的构建、测试及静态检查；没有新变更、失败或未解决疑虑时，不因恢复上下文重复跑已确认通过的整套检查。共享入口变化、阶段验收或仓库要求需要更广回归时再扩大范围；无法验证的部分如实说明。
- 公共组件的最小完整用法优先成为可执行测试，覆盖从入口到结果的主要流程，并便于使用者找到；测试位置遵循仓库约定，不强制重排无关用例。
- 消息映射和批量组装测试使用完整、彼此可区分的合法样本，核对每条记录及槽位的字段对应关系，并区分零值、空字符串、缺失与 `null`。仅验证有输出或数量正确不足以证明映射；副作用也需按契约检查何时应发生、何时不应发生。对照见 [上报测试案例](references/reporting-contract-cases.md#案例三最小链路也要有可辨识的输入)。
- 交付时简要说明改动、验证和遗留限制；仅在有实质取舍时解释设计，不输出冗长自检报告。

## 收到“代码写得不自然”等反馈时

不要要求用户先读懂全部实现并准确指出问题。主动回看需求、本次 diff 和相邻代码，从头寻找概念更少、职责更清楚的实现。必要时推翻原方案，而不是持续修补。能改进时直接修改，并简短解释关键取舍。

## 迭代边界

把偏好反馈当作案例，不立即升级为普遍禁令。提炼工程原则时记录适用条件及反例；优先吸收反复出现、能够在新任务中验证的判断。修改本 Skill 的职责组织原则时，使用 [职责边界回归任务](evals/responsibility-boundaries-regression.md) 检查行为，按设计结果评估，不匹配固定文件名或措辞。未经用户明确要求，不主动修改本 Skill。
