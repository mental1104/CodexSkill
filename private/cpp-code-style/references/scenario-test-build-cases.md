# 测试组织与构建配置案例

## 案例一：让正向场景保持可读

用户希望先通读两条主要成功路径，再单独检查异常。第一版把进程启动、socket、协议编码、临时文件、失败注入和用例正文堆在一个文件；即使函数名正确，也很难看出业务故事。

可以按已有仓库布局表达为：

```text
integration/
  transfer_positive_test.cpp   主要正向场景与业务断言
  transfer_failure_test.cpp    拒绝、重试、取消及清理等已确认异常
fixtures/
  transfer_environment.*      依赖、进程和临时资源管理
  application_client.*        公开客户端、真实反馈与结果收集
```

这些是职责示意，不规定文件名或文件总数。正向正文可读成“准备源文件 → 调用方提交请求 → 观察反馈 → 核对结果和接收端文件”；故障注入的实现细节留在 fixture，核心业务仍由被测实现执行。共享夹具沿用构建目标复用，GoogleTest 执行测试并报告断言结果。

有共享环境与生命周期时可用 `TEST_F`；只有简单输入输出的测试不为统一形式强制引入 fixture。文件已短小、没有独立异常阅读需求时，也可以保持当前布局，不机械拆文件或添加流程 DSL。

## 案例二：编辑器应读取真实目标配置

某个集成测试目标定义了一个启用协议层的宏，并依赖构建生成的头文件。实际 CMake 目标编译成功，编辑器却把宏内代码标灰或提示生成头不存在。只把宏塞进编辑器配置，会让代码显现，却未解决生成目录和实际参数不一致。

按以下顺序处理：

1. 确认当前打开的工作区、实际目标和构建目录，读取该文件的真实编译记录。
2. 核对宏、include、编译器和语言标准是否来自同一目标；先配置并构建必要的生成目标，确认头文件实际存在。
3. 让 CMake provider 或编译数据库指向这套配置。同一源文件被不同目标用不同宏编译时，显式选定用户要读的目标，避免误取第一条记录。
4. 按已确定的差异修改生效的工作区配置；生成目录随构建树引用，不复制生成头文件到源码目录，也不手工修改生成文件。
5. 核对配置已与实际编译一致。无法检查编辑器实时状态时说明限制，不声称已经验证界面中的灰色或红线消失。

不要为让编辑器显示代码而增加仅编辑器可见的生产条件分支。手工配置只有在工具无法提供目标参数且能与真实构建保持一致时才作为明确备选，不能仅添加宏而忽略其他依赖。

反向情形：真实编译也报错时，应检查缺失依赖、自包含头文件或源代码问题，不能一概归因于索引缓存。普通单元测试目标仍按自身参数编译，不因浏览集成测试就强制启用整个集成 suite。

## 案例三：配置一次后的容器测试生命周期

用户明确要求在配置阶段选择普通模式或容器集成模式，后续只使用默认构建、测试与清理命令。第一版虽然有开关，仍需每次给 `make test` 追加日志参数，测试阶段还可能隐式重建环境，没有兑现这个约定。

以用户指定的 Makefiles 工作流为例：

| 阶段 | 普通模式，默认关闭容器集成 | 明确启用容器集成模式 |
|---|---|---|
| CMake 配置 | 原有编译与测试配置 | 固定模式、必要工具检查、默认测试输出及环境身份；此阶段不部署 |
| `make` | 编译原有目标 | 构建测试需要的产物/镜像，启动本轮环境并等待可用 |
| `make test` | 执行已注册普通测试 | 只执行所选集成场景，不重建镜像或重启环境；环境未准备时提示先构建 |
| `make clean` | 原有构建清理 | 回收本构建目录拥有的测试环境，保留证据，再完成约定的产物清理 |

将已选择的默认输出选项保存在构建配置中，不让用户每轮重输 `ARGS`。筛选、排错等额外参数仍可按需使用。用户要在根 CMake 顶部一行 Boolean 切换时，提供一个清楚的入口，并说明它与 cache / 命令行覆盖的关系；验证复用已有构建目录切换模式，避免旧缓存令开关无效或多份设置相互遮蔽。

镜像内部编译服务和客户端，与宿主机编排容器是两个入口。通过已有参数或独立构建目标令镜像内走正常编译，不能因复制同一份启用集成的 CMake 配置而再次启动 Docker。清理入口也不能依赖已经被 clean 删除的驱动；验证重复 clean、失败后的回收和仅清理本轮资源。

用户要求宿主机测试驱动不依赖 Python 时，检查 CMake 查找、容器编排、就绪探测、结果解析与清理中的实际调用，迁移整个约定的运行链，而非仅把 fixture 写成 C++。这不要求删除用户另行需要的 Python 手动 demo，也不等于镜像内接口生成工具不能使用 Python。

两种模式若被用户明确要求互斥，可以只注册各自测试；普通 integration opt-in 仍不默认隐藏 Unit Test。用户临时先建设集成测试时按本轮范围调整，不自动删除已有单测或改变其他项目策略。

反向情形：只新增普通 C++ 单测时，不引入容器模式或修改 clean。仓库已有 CTest fixture 自动准备环境的约定、且用户未要求上述生命周期时，继续沿用；不要把本案例变成所有 CMake 工程必须遵守的部署方式。

## 案例四：本地调试接口不能代替正式构建依赖

依赖仓库的正式版本尚未发布新消息，用户允许在临时分支生成并本地安装以调试。应用因此可以编译，但 CI 仍拉取旧依赖分支，缺少生成头文件。这是依赖来源不同，不能用“本地全测通过”证明正式构建也可用。

```text
调试：临时接口源 → 本机生成/安装目录 → 应用构建通过
交付：CI 依赖清单 → 实际解析的版本 → 生成头与 typesupport → 应用构建
```

记录调试覆盖的包、来源版本与构建/安装前缀，保留用户指定的“不合主线”等边界。交付前核对正式依赖是否确实含所需定义，清单和实际编译参数是否读取它；从正式来源生成并在不依赖本机调试覆盖的干净构建环境中验证。检查 include 通过与链接所需的生成库、运行时支持分别说明，不只复制一个头文件掩盖依赖。

按当前任务授权更新依赖清单；优先使用工具支持的不可变版本。只能使用可变分支时记录实际解析提交，并明确它仍会移动；记录当时 SHA 不等于已固定依赖，更不能因此宣称完全可复现。不要为修一个依赖缺口改写整条流水线或合入仅供调试的接口仓库。

反向情形：仅做本地接口原型时，可以如实交付调试结果和正式依赖缺口，不要求先合并依赖才能继续；只授权评估 CI 时不发布修改。未运行目标平台完整 CI，就区分清单校验、接口生成、局部编译与完整流水线验收。
