# 后端契约与借用接口案例

这两个案例分别用于判断共同校验应放在哪里，以及如何减少调用方对内部拥有者结构的依赖。它们不要求所有组件采用相同模式或接口名称。

## 案例二：公共校验入口

### 场景与证据

common 的三个 JSON 后端各自执行相同的空输入和原始 NUL 检查。用户要求避免后续派生类继续重复，并提出装饰器。助手说明固定公共入口加虚函数钩子（NVI）能让共同契约始终执行，而可选装饰器可能被绕过；用户明确接受，并要求高频路径保持轻量。

来源：code_stype_2.md 第 3、5080、5105 行。

### 收敛后的判断

既有多态体系中，把所有后端必须遵守的检查放在公共入口，派生类只实现后端钩子。此次实现使用 final 防止覆盖入口绕过检查；后端仍负责自己的语法、资源创建和特定错误。

收益在于共同契约不再依赖每个新增后端记得实现。无需为此再创建装饰器对象、通用回调层或统一异常捕获。保留既有异常策略，不把分配失败等异常伪装成输入错误。

### 条件改变时

- 可选计时、日志或重试可以独立组合；不因为此案例把它们强制塞入基类。
- 没有既有多态需求时，可以采用直接函数组合，不为消除重复新建继承体系。
- 后端合法输入或错误约定不同，先确认是否真有共同契约；不要把某后端的限制强加给全部实现。
- 抽取校验不自动授权改变检查顺序、接受范围或异常语义。

### 性能证据的边界

该轮 benchmark 比较的是当前统一 API 下加载、成功检查与 DOM 释放的整体成本。用户认可结果并明确不再做旧版对照，因此记录不能证明 NVI 本身提速或零开销，也不能证明某后端对所有工作负载最快。内联是优化机会，不是保证。

## 案例三：拥有者与借用视图

### 场景与证据

原接口要求调用者经由公开的 doc 成员取得根节点，并同时提供 as_optional 与 get_optional 等读取表达。用户要求删除多余入口，隐藏内部文档成员，直接从加载结果取得根节点，完成对象访问、数组遍历与输出。

来源：code_style_1.md 第 51378 行；第 57197 行记录了收敛后的接口及借用约定。

### 收敛后的判断

加载结果内部拥有文档，公共访问入口返回轻量借用视图，输出操作可以接收拥有者。调用方无需理解内部成员布局，也不必学习重复的读取词汇。

封装后仍要明确：视图不延长文档生命周期；移动拥有者后是否保持视图有效取决于底层资源地址；销毁或覆盖拥有者会使旧视图失效。独立复制的值、字符串和输出文本可以比文档活得更久。

### 条件改变时

- 结果本身已经是独立值时，不为“轻量”强行改成借用视图。
- 真有异步持有或跨组件共享生命周期的需求时，可以设计共享所有权；不要只为缩短调用路径换成 shared_ptr。
- 公开成员、旧入口属于已有 API / ABI 契约时，先处理兼容迁移，不能照搬本次删除。
- 删除重复的读取入口不意味着禁止 optional，也不意味着将缺失、合法 null 与读取失败随意混同。
- 通用 JSON 库允许处理未知 schema；固定业务模型由使用它的业务层建立。
