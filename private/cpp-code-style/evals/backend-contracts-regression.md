## 案例二：公共校验入口

### 自然语言任务

一个已有的 C++ 多后端文本解析库，在三个派生解析器里重复检查空输入和原始 NUL。协议已规定这两者非法，转义后的 NUL 合法；公共输入错误先于后端不可用错误，现有后端异常策略不变。

请消除重复，使以后新增解析器也不会漏掉这些检查。正常调用很频繁，保持统一接口轻量，不引入额外功能。调用方还可能需要可选计时，未启用计时时不应因此产生额外包装。沿用现有测试框架和构建入口。

### 应观察的设计

- 共同契约由不可绕过的公共入口保证，后端只负责实现钩子或等价的受约束扩展点。
- 不要求调用方记住装饰每个实例，也不把检查再复制回派生类。
- 可选计时独立于强制校验；没有因统一入口新增堆包装、输入副本或 catch-all。
- 保留原合法输入范围、错误优先级与异常语义，后端特有检查不被无依据提升为公共限制。
- 若采用 NVI，验证派生类无法通过覆盖公共入口绕过校验；不要求固定钩子名称，也不把 inline 当作实际内联的证据。

### 有项目材料时的验证

- 使用记录调用次数与接收输入的后端替身：非法输入不进入后端；合法输入按原字节内容转交。
- 空输入、首个原始 NUL 的错误位置以及转义 NUL 符合既有契约。
- 自定义后端按约定传播异常，后端关闭时维持已有错误优先级。
- 检查直接使用具体解析器和经基类访问时的入口约束；采用 final 时可用独立的预期编译失败探针验证覆盖被拒绝，不把失败源码加入正常构建。 普通非虚方法仍可能被派生类同名方法隐藏，不能仅以“不可 override”证明守卫必经；[成功绕过探针](probes/nonvirtual-entry.cpp)和[预期编译拒绝探针](probes/final-entry-rejection.cpp)用于复核这一区别。
- 运行相关行为测试与项目要求的兼容构建；新增源码不应在同一配置下因多个测试目标重复编译。
- 若进行性能比较，分别标明计时范围与构建条件；没有前后对照时，仅报告当前整体 API 成本。

### 反向场景

自然语言任务：一个单实现库没有继承体系，两个普通入口共享一小段校验；日志和计时只是调用方可选能力。请提出消除重复的最小方案，不扩展支持范围。

应观察：允许直接复用函数；不为套用案例建立继承、工厂或注册表，也不把可选能力变成不可关闭的校验步骤。

## 案例三：拥有者与借用视图

### 自然语言任务

一个通用 JSON 包装库返回加载结果。调用方必须了解结果中公开的文档成员，才能访问根对象、遍历数组和导出文本；当前还有两组用途重叠的可选值读取入口。

请简化这段完整流程。允许调整 C++ 接口并迁移库内调用，本次没有对外 ABI 兼容承诺。保持单一拥有者和轻量借用，不假设输入有固定业务 schema；错误语义沿用现有约定。共享测试辅助源码已经用于多个测试程序，性能测试也有独立执行需求。

### 应观察的设计

- 常用流程无需操作内部文档成员或原生类型；读取入口按语义收敛，不机械增加同义别名。
- 仍能从类型、说明和最小用法理解拥有者与视图的关系；不靠隐式 shared_ptr 或复制整棵树隐藏生命周期问题。
- 说明实际实现中的移动、覆盖和销毁对视图的影响；不声称有效性查询能识别已悬空的视图。
- 通用节点接口允许未知 schema，固定业务类型由调用方按需建立；不删除合法 null 或 optional 语义。
- 最小用法进入测试，沿用项目布局；默认普通测试与性能执行范围分离，同一配置复用业务库与辅助对象，不跨不同编译配置强行复用。

### 有项目材料时的验证

- 经公共 API 完成载入、对象读取、数组遍历、导出与失败检查，不访问内部成员。
- 独立复制的值和导出文本在拥有者释放后仍可使用。
- 按实际资源布局验证移动后的视图约定。销毁或覆盖后只核查失效契约，绝不通过解引用悬空视图来“验证失效”。
- 保留既有缺失、null、类型不符与失败结果测试，并运行适用的调用方编译和链接检查。
- 检查构建规则及普通测试发现结果：共享源码在相同配置下复用，性能测试只经明确入口执行。若仓库已有不同的强制约定，遵循约定并说明。

### 反向场景

自然语言任务：另一个组件直接返回独立拥有的字符串，旧公开成员已被外部调用方依赖并存在 ABI 承诺。请审查能否照搬“隐藏文档并返回视图”的方式。

应观察：不为减少复制强行引入借用，不直接删除受兼容约束的成员；先确认收益与迁移边界，不把案例中的接口形状当普遍规则。

## 测试组织与编辑器配置补充场景

自然语言任务：现有 C++ 集成测试的主成功路径很难读，用户要求正向集中、异常另文件，共享夹具沿用现有构建目标。请整理正文和 fixture 边界，不扩展业务或另建测试框架。

应观察：主要场景保留公开动作和结果断言，机制细节与失败注入可复用；不让 fixture 代做业务，不为拆文件而重复编译共享业务源码。小型单个场景作为反例可以保持原结构。

自然语言任务：一个源文件在普通目标和可选集成目标中分别编译。集成目标需要宏和生成头文件，实际构建成功，但 IDE 读取了普通目标配置。请修复当前工作区的索引配置。

应观察：核对实际目标的完整参数与生成结果后调整 provider 或编译数据库选择；不只塞一个宏，不改合法源表达式或生产条件编译。真实编译失败时不能照搬“只是 IDE 问题”的结论；未验证 GUI 时保留这一限制。

本节同样只定义回归任务；静态核对、场景推演和独立会话实测须分别记录。

## 容器构建模式补充场景

自然语言任务：现有 CMake 工程默认普通编译。用户要求配置时选择容器集成模式，之后直接 `make` 构建并启动环境、`make test` 仅执行用例并默认输出交互、`make clean` 回收测试环境。镜像也用同一源码编译，宿主机运行链不得依赖 Python；另有应保留的 Python 手动 demo。请落实该模式。

应观察：配置保存完整默认行为，镜像内部不递归编排；测试不悄悄重建；清理不依赖已删除驱动且只回收本轮资源。核对 CMake 与辅助探测/报告链的宿主机依赖，不扩大成禁止 Python demo。应验证普通模式、已有目录切换、完整无附加参数流程及重复清理。

反向任务：只给现有 C++ 普通单测增加一个断言，没有容器生命周期要求。应保持原有构建和清理，不新增 Docker、模式开关或 TDD 关卡。

## 判定与记录

补充任务：源消息使用整数和位图，目标上报要求可空数值及嵌套质量对象。用户要求独立输出结构，随后要求复用同义字段的声明。观察是否先构造完整 typed report，再经现有序列化入口输出；字段模板只在名称/单位/原始类型一致、差异集中于包装时使用，源状态、输出质量及转换仍独立。只有同一份生成协议或模型已分化时，不机械复制 schema 或套模板。

补充任务：仓库明确不通过异常报告可预期失败，要求实现队首读取。观察是否区分失败、空队列和有记录，且失败不误删；已有异常契约的普通 API 是反向场景，不全局改为 bool 或 noexcept。

补充任务：本地用了用户授权的临时生成接口，CI 正式依赖缺头。观察是否核对正式清单、真实 include/link 来源与目标平台验证范围；可变分支不声称不可变。纯原型任务只标注正式依赖缺口，不擅自合并或推送接口仓库。

判定依据是契约是否真的保证、生命周期是否成立、调用方是否更容易使用以及范围是否受控。只复述 NVI、RAII 或 benchmark 等术语不算通过。设计说明不能代替编译、运行或前后性能对照的证据。
