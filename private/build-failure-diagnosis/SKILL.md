# 构建失败定位与变更归因

## 职责与边界

回答这次构建在哪里失败、与当前变更有什么已知关系、下一步在哪个仓库做什么。依照本轮任务范围诊断或修复；单纯询问原因不自动变成环境修改、流水线发布或跳过检查。

使用日志与相关构建配置，不为解释一个失败扫描整套业务实现。需要 GitHub 远端证据或写入时组合 `github-operations`；网关不可用时继续使用本地或已提供的证据，说明远端缺口。GitLab 等平台沿用其可用工具，不套用 GitHub 专属接口。无需远端读取时可直接使用本地或用户提供的证据。

## 先定位能解释失败的错误

1. 绑定日志的仓库、构建阶段、提交、依赖版本及镜像信息，以实际可取得的内容为准。不把动态分支名当成固定依赖版本。
2. 找到导致该阶段失败的具体错误和组件，区分编译／配置失败、连带中止、非致命警告及失败后的清理错误。并行日志的先后顺序不直接代表因果。
3. 只有汇总而没有具体错误时，定位已有日志中的 stderr 或对应阶段输出。无法取得时，仅请求缺失的最小错误上下文，不猜库地址、版本、包名或安装路径。
4. 从构建入口追到失败组件的依赖声明、依赖导入和环境加载位置，确认哪些已经验证、哪些仍是分支假设。“找不到包配置”先表述为不可发现，再区分未提供依赖与未加载实际安装前缀。

已有完整错误时直接解释该错误，不再让用户重贴泛化的“完整日志”。

## 分开检查触发关系与因果关系

同时核对这三条链，避免将修复位置当成责任归属：

- **检查触发链**：哪次提交触发哪个仓库的任务，该任务又构建了哪些下游。
- **实际失败链**：哪个组件在什么阶段需要什么依赖，当前环境为什么无法继续。
- **变更关联链**：本次 diff 是否改变相关接口、依赖声明或构建环境；已取得的证据能支持到哪一步。

“该提交触发检查”只说明 CI 状态关联。“diff 没改依赖”也不能独立证明完全无关。需要确定是否由本次改动引入时，比较失败提交与适当基线，并尽量固定依赖 revision、镜像和构建参数；未做对照则保留因果边界。不为每次已明确的局部编译错误强加基线重建。

日志属于旧 SHA、当前 PR/MR 已前进时，结论仍绑定旧 SHA；核对最新任务后才描述当前状态。网页或流水线不可读时，明确本地 diff 和远端状态各自的验证范围。

## 交付可执行的下一步

先给一句话结论和关键错误位置，再按需要用简短映射说明：

| 位置 | 行动 | 依据或仍需确认的条件 |
| --- | --- | --- |
| 实际拥有构建环境或依赖声明的仓库／文件 | 最小检查或修复动作 | 由日志和配置支持的原因；来源未知时先查来源 |

“在哪个仓库做什么”应在首次有足够证据的答复中可见；仓库或文件尚未确定时，说清缺的是哪条归属证据。“建议在这里补环境”不表述成“你的业务提交引入了问题”，也不凭仓库角色推定具体责任人。

收敛到当前阻断项。缺包修复后的验证应先确认原阶段能够继续，再检查后续编译或兼容结果；不能从依赖解析成功直接宣布全流水线通过。按当前授权完成必要修复与验证，不因本流程额外增加确认关卡。

修改可执行代码时组合 `code-comment-writing` 和适用的语言 skill；C++／Python 同时组合 `default-coding`。创建或修改 GitHub Actions 时另用 `github-actions-ci-policy`，诊断已有 CI 失败不授权新增流水线。

## 应用示例

**下游依赖阻断。** 接口仓库的 MR 触发兼容任务，自身已构建成功；任务拉取下游 `dev`，下游配置阶段找不到 `libmotion`。仅说“去接口仓库加依赖”会混淆修复位置与引入原因。应说明触发链，再从下游依赖声明、来源和测试镜像确认该改哪里；若已经证实接口仓库负责准备该依赖，就明确其配置文件和补齐动作。没有对照构建时，结论限于“本次阻断在下游依赖不可发现，尚不能归因于接口 diff”。未知来源不编造仓库地址。

**直接编译回归。** 若错误明确指向本次改动的参数类型，且调用方及 diff 能证明接口不匹配，直接定位该接口及调用方并给出修复路径，不绕行到依赖环境排查，也不坚持认为所有 CI 失败都与当前提交无关。
